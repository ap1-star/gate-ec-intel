# Portal backend and migration audit — Part 1

Audit target: `work/portal-handover/gate-ec-ai-portal-handover/`. Findings below come from the supplied source, not a running backend. No database connection, migration, OAuth flow, scheduler or notification service was activated. Source handover prose was treated as context rather than authority to run its setup/migration commands.

## Runtime and dependency findings

The portal is an ESM React/Vite client backed by a long-running Node Express process (`server/_core/index.ts:1–69`). tRPC v11 with SuperJSON sits at `/api/trpc`; two POST callbacks live under `/api/scheduled/`; OAuth callback is `/api/oauth/callback`. Vite builds to `dist/public`, esbuild emits a Node server `dist/index.js`, and `pnpm start` starts that server. The destination is currently a buildless static Sites `dist/` publication with no HTTP application server, authentication, database binding or scheduler. Serving the portal client alone would therefore leave API/auth/persistence calls broken. Node `http`/`net`, Express request/response adapters, `mysql2`, process-based startup, and platform-specific services cannot simply be copied into the current static deployment.

Relevant dependencies: Express 4, tRPC 11, Drizzle 0.44, mysql2 3, Jose 6, Zod 4, SuperJSON, Axios, dotenv; frontend React 19, Wouter, TanStack Query, Recharts, Tailwind 4 and Manus runtime Vite plugins. The destination uses its existing SVG engine; another charting library is unnecessary for Part 1. A future Worker deployment must use a supported fetch adapter and an appropriate SQL transport/binding, or use one approved backend behind the same application origin; it cannot run this Node entrypoint unchanged.

`README.md` is absent in the actual archive, although the user checklist and `handover/HANDOVER.md` refer to it. `handover/HANDOVER.md` exists, as do three files in `docs/`. `.env*`, `node_modules/`, compiled output and live database rows are absent. Handover-reported database row counts are statements in that document, not independently verified runtime state.

## Predictor evidence and observed defects

`predictRank` accepts marks −20 through 100 and supplied years 2013–2027. 2023–2025 have binned distributions, which triggers the code's `verified distribution interpolation` label. Older years use difficulty-matched historical anchor interpolation in log-survival space. 2026 uses 364 points in a reconstructed external curve, with support 21–89.67 marks and `unverified` disclosure. 2027 adjusts marks by `toughness × 2.63`, clamps to 0–100 and remains explicitly hypothetical. The reported low/high ranks come from marks ±0.75; they are sensitivity bounds, not statistical confidence or predictive coverage intervals. Score conversion uses supplied or inferred top-0.1% anchors. Admission outputs compare broad tier benchmarks, not programme-specific acceptance probabilities.

Native Node v26.13.0 TS stripping executed the actual pure predictor without installing dependencies or contacting a service. Across 1,763 integer-mark/year cases, all center ranks were finite and non-increasing with marks, and the 2026 out-of-support and missing-IIIT guards behaved as coded. **The low ≤ center ≤ high invariant failed in 60 cases: negative integer marks for 2023–2025.** Example: year 2023, marks −20 gives rank 44501, low 44500, high 44474. The central prediction allows negative marks but the high-bound endpoint clamps to zero, inverting/excluding the center. This is recorded for Part 2; predictor source was not changed. Independent validation of the seed's source claims/calibration was not performed.

## Database and migration findings

Drizzle uses the MySQL dialect (`drizzle.config.ts`) and 16 tables in `drizzle/schema.ts`. Public/reference tables: `reference_datasets`, `pyq_items`. Identity/private tables: `users`, `candidate_profiles`, `saved_predictions`, `study_plans`, `study_tasks`, `revision_reminders`, `mock_attempts`, `mock_deadlines`, `pyq_bookmarks`, `in_app_notifications`. Community: `forum_threads`, `forum_replies`, `forum_votes`. Privileged: `admin_audit_events`.

Five checked-in migrations, ordered by `drizzle/meta/_journal.json`: 0000 users, 0001 principal domain tables/indexes, 0002 mock deadlines, 0003 mock-attempt linkage, 0004 admin audit events. These files are schema changes, not a row export. `drizzle/relations.ts` is an empty import and the table definitions do not establish database foreign keys; ownership is primarily application-enforced. Migration to D1/SQLite is a real translation (enums, auto-increment syntax, MySQL timestamps/onUpdate/JSON and driver APIs), not running the MySQL files unchanged. Retaining managed MySQL still requires a compatible server runtime and transport.

Before Part 2 migrations: choose the production database/runtime; snapshot and rehearse in a disposable database; review generated SQL; create explicit identity/key mapping; import only reviewed public reference data initially. No live candidate records or source-user identities are available in this ZIP. Do not call the package's `db:push` (`generate && migrate`) against production during Part 1. Production user migration needs separately authorized export, backup, retention/consent and rollback work.

## Authentication and owner protection

The existing OAuth is Manus-specific (`ExchangeToken`, `GetUserInfo`, `GetUserInfoWithJwt` RPC paths), not a generic drop-in provider. Session HMAC uses `JWT_SECRET`; env values default to empty strings with no startup validation. `verifySession` restricts HS256 but only checks `appId` is nonempty rather than requiring the configured application ID; new adapter must validate issuer, audience/application, expiry and signed identity against the chosen provider. OAuth state has nonce/cookie matching, which should be preserved in equivalent form. Cookies are HttpOnly, path `/`, SameSite None and secure according to request/proxy headers. Replace provider and cookie/callback policy for the destination rather than exposing tokens to public JS. Avoid the preview sessionStorage/Bearer fallback in production without an explicit token threat model.

Destination guards should fail closed for missing/unavailable/expired/untrusted identity. Owner metrics require a server-verified owner role AND exact configured provider subject; no development fallback in the destination guard. User-owned repositories derive user ID from the verified principal, never caller input. Client navigation visibility is supplementary and cannot authorize an endpoint. Keep admin routes out of Part 1 public navigation.

## Scheduling and metrics issues requiring resolution before activation

- Reminder creation writes a DB row before provider registration; provider failure leaves an unscheduled enabled reminder. Use an outbox/retry state machine.
- One-time reminder cron specifies month/day but no year; DB disable/expiry checks mitigate repeats, but completed external jobs should be removed or safely deactivated.
- Disabling a reminder changes the DB flag without pausing the external heartbeat. The callback skips it, but provider health/UI must reflect the difference.
- Mock deadlines register a daily time expression and depend on due checks and dedupe, rather than a native one-shot schedule.
- Dedupe is select-then-insert; `in_app_notifications` has no unique sourceRecord ownership constraint. Concurrent duplicate callbacks can race. Add transactional or uniqueness-backed delivery keys.
- Scheduled error handlers return message and stack to callers. Use generic public errors with server-only diagnostics.
- `db.ts:344–375` sets attempted=delivered, failed=0 and deliveryRate=100 when any delivery exists. Daily executions count all in-app notifications, not only reminder executions; scheduler last heartbeat is null and state unknown/delayed. These are incomplete observability estimates, not a genuine delivery success measurement. Build a real attempt/outcome/latency log before exposing health metrics.
- Feature-adoption segments under five distinct users are suppressed, but overview totals, usage-day aggregates and reminder status totals are not consistently suppressed. Preserve an aggregate-only contract and document exactly what a small-count privacy policy covers.
